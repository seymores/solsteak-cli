# Release validation

## v1 foundation

Validated on macOS Apple Silicon (`arm64`) with Rust 1.99.0.

- `cargo build --release --locked` produced `target/release/ssteak`, a Mach-O
  64-bit arm64 executable.
- `otool -L` reports only macOS system libraries/frameworks: Security,
  CoreFoundation, libiconv, and libSystem. SQLite is bundled; no database server
  or Rust runtime is needed to run the binary.
- Strict clippy, formatting, and the complete fixture/mock test suite pass.
- The supplied public wallet was inspected live through Helius: 10 selected stake
  accounts, 8 validator groups, all 10 latest completed-epoch reward records, and
  an exact recorded subtotal of 58,447,695 lamports. This is a point-in-time
  observation, not a guarantee about future provider availability.
- Pseudoterminal and frame checks cover cleanup, signals, a full offline launch,
  80×24/120×35 layouts, resize, and 1,000 rows. The renderer avoids background
  color assumptions and deterministic frame tests cover no-color mode. Manual
  inspection on a user's light and dark terminal themes remains recommended.

Install locally by copying `target/release/ssteak` to a directory on `PATH`, set
`HELIUS_API_KEY`, then run `ssteak -a <public-address>`. `--offline` needs no key.
The first online inspection creates the private SQLite file in the platform data
directory; preserve it before manual recovery if storage reports an error.

## 15-epoch reward history (schema v2, superseded by the 30-epoch window below)

Validated on macOS Apple Silicon (`arm64`) with Rust 1.99.0, uncommitted work on
top of `66122e3`.

- `cargo fmt --check`, strict clippy (`-D warnings`), and the complete
  fixture/mock `cargo test --locked` suite pass; `cargo build --release --locked`
  produces a Mach-O arm64 executable linking only the same system libraries.
- All six schema-v2 examples validate against `docs/contracts/report.schema.json`
  (checked with Python `jsonschema` in a scratch environment, not a project
  dependency); the retained v1 examples validate only against
  `report.v1.schema.json`. Negative cases (`input.epochs`, `INVALID_EPOCHS`, more
  than 15 epochs, a return on a non-recorded entry, a non-string percentage, a
  missing `account_return`) are rejected.
- Mock call budget, one stake account, cold: genesis, epoch, input account, 15
  reward requests, closing epoch check = 19 requests. Warm same-epoch reload: 3.
  One-epoch rollover: 5 (one new reward request). Shortened chain (3 completed
  epochs): 3 reward requests. Supplied-wallet fixture (10 accounts): 22 requests
  including 15 reward requests. These are mock counts, not provider measurements.
- Frame tests cover the Account Detail chart at 80×24 and 120×35 in monochrome.
  Manual light/dark terminal inspection of the chart is still recommended.
- Live validation (supplied public wallet, user-supplied key, isolated temporary
  home so no existing database was touched; no credential recorded): a cold
  `--json` run returned status complete in about 4.8 s for 10 stake accounts and
  8 validator groups. The window was 15 epochs (1050 down to 1036) with all 150
  account/epoch rewards recorded, and the report held exactly 15 reward sources,
  i.e. 15 `getInflationReward` requests (one batch of 10 per epoch). With the
  fixed discovery flow that is 22 requests in total, matching the mock count; the
  total is inferred from the report, not counted on the wire. A rerun within 60 s
  reused every cached reward (15 cached reward sources, about 0.14 s). Latest-epoch
  subtotal 58,447,695 lamports; per-account estimates ranged from 0.3204% to
  3.3011%. `--epochs` was rejected with exit 2 and no network use. This is a
  point-in-time observation, not a provider guarantee.

`--epochs` is rejected with `INVALID_ARGUMENTS` before any storage, network or
terminal setup. Version-1 snapshot reports in an existing database are not served;
one online refresh writes a version-2 snapshot while durable rewards are reused.

## 30-epoch window with current-vs-previous comparison (schema v2 amended)

Validated on macOS Apple Silicon (`arm64`) with Rust 1.99.0, uncommitted work on
top of `66122e3`. Report schema 2 never shipped, so it was amended in place.

- `cargo fmt --check`, strict clippy (`-D warnings`) and the complete fixture/mock
  `cargo test --locked` suite pass.
- All seven schema-v2 examples validate against `docs/contracts/report.schema.json`
  (Python `jsonschema` in a scratch environment, not a project dependency); the
  retained v1 examples validate only against `report.v1.schema.json`. Seven
  negative cases (31 epochs, missing `comparisons`, non-integer difference,
  16 pairs, a negative unsigned mean, a 2-decimal percent, an extra field) are
  rejected.
- The examples' estimates and comparisons were generated by an independent Python
  implementation, and a Rust test recomputes them and requires an exact match.
- Mock call budget, one stake account, cold: genesis, epoch, input account, 30
  reward requests, closing epoch check = 34 requests. Warm same-epoch reload: 3.
  One-epoch rollover: 5 (one new reward request). Shortened chain (3 completed
  epochs): 3 reward requests. Supplied-wallet fixture (10 accounts): 37 requests
  including 30 reward requests. These are mock counts, not provider measurements.
- Frame tests cover the paired chart at 80×24 and 120×35 in monochrome. At 80×24
  the chart has one bar row; the period summary, bars, caret and selected pair are
  visible and the legend, latest estimate and attribution scroll into view. Manual
  light/dark terminal inspection is still recommended.
- Live validation (supplied public wallet, user-supplied key, isolated temporary
  home so no existing database was touched; no credential recorded): a cold
  `--json` run returned status complete in about 7.8 s for 10 stake accounts. The
  window was 30 epochs (1050 down to 1021) with all 300 account/epoch rewards
  recorded and no errors or findings, and the report held exactly 30 reward
  sources, i.e. 30 `getInflationReward` requests (one batch of 10 per epoch). With
  the fixed discovery flow that is 37 requests in total, matching the mock count;
  the total is inferred from the report, not counted on the wire. A rerun within
  60 s reused all 30 cached reward sources (about 0.14 s). The 120-second deadline
  held with wide margin. All 10 accounts compared 15 of 15 pairs; for each, the
  current 15 epochs' reward subtotal was 19.2% to 19.4% lower than the previous 15
  (mean estimate 0.08 to 0.83 percentage points lower). That is a point-in-time
  descriptive observation for this wallet, not an explanation and not a provider
  guarantee.
